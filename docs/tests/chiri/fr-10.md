# FR-10: Prediction request discipline - Test Plan

| Field | Value |
|---|---|
| Requirement | [FR-10](../../prd/chiri/index.md#fr-10-prediction-request-discipline) |
| Priority | P0 |
| Scenarios | 14 |
| Last updated | 2026-07-28 |

## What this requirement promises

Chiri only asks the model for a continuation when the writer has genuinely paused, never on every keystroke.
A request that becomes stale, because the writer kept typing or moved the caret away, is cancelled and its eventual answer is thrown away rather than shown.
Fast typing cannot flood the provider: there is a ceiling on how many continuation requests can be in flight at once and how many can be sent per minute, and a request dropped for either reason is silent, with no error shown to the writer.
Revision and refinement requests, which the writer explicitly asked for, are never subject to any of this: they are not debounced, not cancelled by the scheduler, and not dropped.
The on/off switch for continuation prediction itself persists across reloads.

## Preconditions

The user has a valid OpenRouter key and has passed the key gate (FR-1).
The editor (FR-3) is loaded and, unless a scenario says otherwise, the document already contains at least one paragraph so the caret can sit at an eligible position for continuation (FR-5 defines eligibility; this plan assumes an eligible position throughout except where stated).
Continuation prediction is on (its default state) unless a scenario is specifically about the off switch.
Whether a given pause actually crosses the "settle threshold" and how many requests fit in "the per-minute ceiling" are exact values the PRD explicitly leaves to the future architecture document; this plan uses the technical blueprint's stated first-party starting values, 600ms and 20 requests per minute with a single in-flight continuation slot, as illustrative concrete numbers and flags them in Open Questions as subject to change.

## Scenarios

### T-FR-10-1: Continuous typing for 60 seconds never issues a continuation request
**Priority:** P0
**Covers:** AC-10.1

**Given** an eligible caret position at the end of the paragraph "Chiri helps you draft faster than"
**When** the user types at a steady cadence of roughly 5 keystrokes per second, with no gap between keystrokes exceeding 400ms, for a full 60 seconds
**Then** no continuation request is ever dispatched during that interval
**And** no ghost text ever appears while typing continues

**How you would run this:** Fully automatable and fast. The technical blueprint describes the scheduler as a dependency-free core module with an injected clock and an injected transport, and states this exact assertion (AC-10.2's sibling) is the first test written, needing nothing running.

### T-FR-10-2: A pause past the settle threshold issues exactly one request
**Priority:** P0
**Covers:** Beyond the stated criteria

**Given** the user has just typed "and gets useful help without reading any" at an eligible caret position
**When** the user stops typing and 700ms elapse with no further input
**Then** exactly one continuation request is dispatched
**And** no second request is dispatched while that one is in flight

**How you would run this:** Fully automatable and fast, using the scheduler's injected clock to advance time and a fake transport to observe the single dispatched call.

### T-FR-10-3: A new pause cancels the prior in-flight request before issuing a new one
**Priority:** P0
**Covers:** AC-10.2

**Given** a continuation request is in flight, issued after the user paused following "Rereading, the user decides the second paragraph"
**When** the user resumes typing "is too long and" and then pauses again past the settle threshold
**Then** the first request is cancelled before the second one is dispatched
**And** at no point are two continuation requests in flight at once
**And** if the first request's response arrives after cancellation, nothing from it is ever shown

**How you would run this:** Fully automatable and fast, using a fake transport whose calls can be individually cancelled and inspected, per the blueprint's injected-transport testing seam.

### T-FR-10-4: A response for a region the caret has left is discarded silently
**Priority:** P0
**Covers:** AC-10.3

**Given** a continuation request was made while the caret sat at the end of the sentence "The user copies the Markdown to the clipboard"
**When** the user clicks into an earlier paragraph, moving the caret away from that region, and the request's response then arrives
**Then** nothing is displayed at the caret's new position or at the old one
**And** the document text is byte-identical to what it was before the response arrived
**And** no error or notice is shown

**How you would run this:** Fully automatable and fast, using the caret-generation guard described in the blueprint: dispatch a request, change the caret generation, then resolve the fake transport's response and assert no state write occurs.

### T-FR-10-5: Rapid caret movement without typing still cancels cleanly
**Priority:** P1
**Covers:** Beyond the stated criteria

**Given** a continuation request is in flight for the caret position at the end of "and closes the tab, and on returning later"
**When** the user clicks to three different positions in the document in quick succession, each less than 300ms apart, without typing
**Then** each caret move cancels whatever request was in flight for the previous position
**And** at most one request is ever in flight at a time
**And** the final resting position, if eligible, may have its own fresh request issued only after that position has settled for the full threshold

**How you would run this:** Fully automatable and fast on the scheduler core module with a fake transport and a scripted sequence of caret-generation changes.

### T-FR-10-6: The per-minute ceiling silently blocks further requests once reached
**Priority:** P0
**Covers:** AC-10.4

**Given** the user has already triggered 20 continuation requests within the current 60-second window by repeatedly pausing and resuming across a long document
**When** a 21st pause past the settle threshold would normally trigger another request
**Then** no request is sent for that pause
**And** no error, warning, or any other message is shown to the user
**And** editing continues without interruption

| Case | Requests already sent in the current window | Next pause behavior |
|---|---|---|
| Just below the ceiling | 19 | Request is sent normally |
| At the ceiling | 20 | Request is sent normally (this is the last one the window permits) |
| Just above the ceiling | 21st attempt in the same window | No request is sent, silently |

**How you would run this:** Fully automatable and fast, driving the scheduler's token bucket with an injected clock so the "same 60-second window" is simulated rather than waited out.

### T-FR-10-7: Turning continuation off persists across reload
**Priority:** P0
**Covers:** AC-10.5

**Given** continuation prediction is currently on
**When** the user turns it off and then reloads the page
**Then** the setting still reads off after reload
**And** no continuation request is issued anywhere in the document after reload, even at an eligible caret position after a long pause

**How you would run this:** The setting-write and setting-read can be tested fast and in isolation against the injected Settings interface (`localStorage`, read once at boot, per the blueprint).
Confirming the reloaded page genuinely issues no request needs a real browser, since it depends on the scheduler wiring at boot; run that half under Playwright.

### T-FR-10-8: Turning continuation off leaves FR-6 revisions unaffected
**Priority:** P0
**Covers:** AC-10.6

**Given** continuation prediction is off
**When** the user selects a paragraph and asks for a revision through the action bar
**Then** the revision request is sent and a result is returned exactly as it would be with continuation on
**And** the revision can be accepted, rejected, and refined normally

**How you would run this:** Needs a real browser under Playwright, since it exercises selection, the floating action bar, and the revision lifecycle together, none of which the pure core module touches.

### T-FR-10-9: The settle-threshold boundary determines whether a request fires
**Priority:** P1
**Covers:** Beyond the stated criteria (boundary probe on AC-10.1's "settle threshold" wording)

**Given** an eligible caret position at the end of "They form a judgment about whether the AI"
**When** the user pauses for the durations in the table below before resuming or letting the request fire
**Then** the request is issued only once the pause reaches the threshold

| Case | Pause duration | Request issued |
|---|---|---|
| Just below threshold | 550ms, then user resumes typing | No |
| At threshold | 600ms of silence | Yes |
| Just above threshold | 650ms of silence | Yes |

**How you would run this:** Fully automatable and fast against the scheduler's injected clock.
The exact threshold value is owned by the future architecture document per the PRD, so this scenario should be re-pointed at whatever value is actually chosen rather than treated as fixed at 600ms.

### T-FR-10-10: Revision and refinement requests are never debounced, cancelled, or dropped
**Priority:** P0
**Covers:** Beyond the stated criteria (the closing paragraph of FR-10's detail)

**Given** the continuation per-minute ceiling has already been reached for the current window, per T-FR-10-6
**When** the user selects a sentence and clicks "Make it shorter", then immediately types a refinement instruction "less formal" before the first result finishes streaming
**Then** both the initial revision request and the refinement request are sent without being debounced, superseded, or blocked by the continuation ceiling
**And** neither request is dropped for concurrency or per-minute reasons

**How you would run this:** Fully automatable at the scheduler-core level to confirm revision requests bypass the token bucket and single-flight guard entirely, per the blueprint's statement that revision and refinement requests "bypass it entirely."
A Playwright-level confirmation that the visible result still appears is a useful companion but the core assertion is at the scheduler layer.

### T-FR-10-11: A dropped or cancelled continuation never surfaces as an error
**Priority:** P1
**Covers:** Beyond the stated criteria

**Given** a continuation request is cancelled because the caret moved, and a separate continuation request is silently dropped because the per-minute ceiling was reached
**When** either event occurs
**Then** no toast, banner, inline message, or any other visible indication appears
**And** this is true even though FR-12 requires visible failure messages for revision and refinement failures, because a cancelled or dropped continuation is not a failure the user asked about

**How you would run this:** Fully automatable and fast at the scheduler-core level, asserting no error-surfacing call is made on cancellation or ceiling-drop paths.

### T-FR-10-12: Typing stays responsive while requests are cancelled or throttled
**Priority:** P1
**Covers:** Beyond the stated criteria (cross-cutting, NFR-2)

**Given** a document of roughly 20,000 characters, at the practical ceiling the PRD names
**When** the user types continuously for 30 seconds while continuation requests are repeatedly issued, cancelled, and throttled by the per-minute ceiling in the background
**Then** every keystroke renders without a perceptible delay, consistent with the keystroke-to-render bar in NFR-2
**And** the in-flight or throttled request state never blocks or delays input

**How you would run this:** Needs a real browser under Playwright with the actual `EditorView`, since keystroke-to-paint timing at this document size is unverified per the technical blueprint's own open question on whether 20,000 characters plus live decorations stays under the 50ms bar; this scenario is the check that answers that question for the FR-10 slice of the work.

### T-FR-10-13: Repeated toggling of the setting persists only the final state
**Priority:** P2
**Covers:** Beyond the stated criteria

**Given** continuation prediction starts on
**When** the user turns it off, back on, and off again in quick succession, then reloads the page
**Then** the setting reads off after reload, matching the last change made before the reload
**And** no intermediate state is what persists

**How you would run this:** Fast and automatable against the injected Settings interface; a single companion Playwright run confirms the real `localStorage` write ordering.

### T-FR-10-14: No request is ever attempted with nothing to predict from
**Priority:** P2
**Covers:** Beyond the stated criteria

**Given** a brand-new, completely empty document with the caret at position zero
**When** the user pauses at that position for well over the settle threshold, for example 2 seconds, without having typed anything
**Then** no continuation request is dispatched
**And** the FR-11 onboarding cue, not a continuation, is what the user sees

**How you would run this:** Fully automatable and fast at the scheduler-core level, confirming eligibility gating (owned by FR-5) and request dispatch (owned by FR-10) compose correctly at the one boundary where they touch.

## Boundaries checked

| Value or limit | Just below | At | Just above | Scenario |
|---|---|---|---|---|
| Settle/pause threshold before a request may fire | 550ms (no request) | 600ms (request fires) | 650ms (request fires) | T-FR-10-9 |
| Per-minute continuation request ceiling | 19th request in the window (sent) | 20th request in the window (sent, ceiling reached) | 21st request attempted in the same window (silently dropped) | T-FR-10-6 |
| Concurrent in-flight continuation requests | 0 in flight (new request allowed) | 1 in flight (ceiling for continuation) | A 2nd request attempted while 1 is in flight (forces cancellation of the 1st, never two simultaneously) | T-FR-10-3 |

## What will probably break

The technical blueprint's "What Will Bite" section names Safari's real abort behavior as unproven: probe 3 only exercised Playwright's WebKit build over a same-origin connection, not Apple's CFNetwork stack cross-origin.
T-FR-10-3, T-FR-10-4, and T-FR-10-5 all depend on cancellation actually severing the connection; expect a real Safari.app run to reveal a cancelled continuation whose stream keeps delivering chunks that the generation counter has to silently discard rather than one that stops at the socket.

The per-minute ceiling and single-in-flight slot are both scheduler-internal state with no telemetry to observe them by, per Non-Goal 9; expect T-FR-10-6 and T-FR-10-11 to be the first place a genuine implementation bug (a request silently dropped for the wrong reason, or one that should have been dropped but was not) looks identical to a network blip, and to be hard to diagnose without deliberately instrumenting the fake transport in the test itself.

Expect the caret-generation guard in T-FR-10-4 to be right in the common case, click somewhere else, and wrong in the case that actually matters for a writer: the user pauses, moves the caret briefly to reread a sentence, and returns to the exact original position before the response arrives.
Whether that counts as "the caret has left its region" or as a still-valid position is not specified by the PRD and is exactly the kind of case a generation counter implemented as a simple integer bump gets wrong by treating every move as a new generation regardless of return.

Expect T-FR-10-10 to be the scenario that catches an implementation where the per-minute token bucket was wired as a single shared limiter across both continuation and revision traffic, because the PRD's instruction that revision and refinement requests are "not debounced or dropped" is easy to implement correctly for debouncing and easy to implement incorrectly for the ceiling, since both mechanisms plausibly live in the same scheduler module.

## Not covered here

Whether a given caret position is eligible for continuation at all, fenced code blocks, mid-word, link targets, is FR-5's trigger-condition logic and is tested in FR-5's plan, not here; this plan assumes an eligible position except in T-FR-10-14.
The content and truncation of the continuation text itself, the two-sentence ceiling, duplicated-tail suppression, is FR-5's concern; FR-10 only governs whether and when a request is sent, not what comes back.
The selection action bar's appearance and the revision lifecycle's accept/reject/refine mechanics belong to FR-6 and FR-7's plans; this plan only asserts that FR-10's scheduler does not interfere with them.
Provider-side failure classes, network unreachable, rate-limited, malformed response, belong to FR-12's plan; this plan's silent-drop scenarios (ceiling and cancellation) are a different thing from a provider failure and are kept distinct on purpose.
Permission and multi-user visibility checks are not applicable: Chiri has exactly one user per browser profile and no accounts, per Non-Goal 3.

## Open questions

The PRD explicitly defers the exact settle-threshold duration and the exact concurrent/per-minute ceiling values to the future architecture document.
This plan uses the technical blueprint's stated first-party starting values, a 600ms settle debounce, a single in-flight continuation slot, and a token bucket of 20 requests per minute, as concrete illustrative numbers so the boundary scenarios are runnable, but T-FR-10-6 and T-FR-10-9 should be re-pointed at whatever values are actually shipped if they differ.

Whether the per-minute ceiling and single-in-flight slot are scoped to continuation requests only, or shared with revision and refinement traffic, is ambiguous.
The PRD states revision and refinement requests are "not debounced or dropped," which reads most naturally as full exemption from every FR-10 mechanism including the ceilings, and T-FR-10-10 defaults to that interpretation.
If instead revisions share the per-minute bucket with continuations, T-FR-10-10 would need to assert the opposite, that a revision can still be blocked once the shared ceiling is hit.

Whether a caret that leaves its original region and then returns to the exact same position before a response arrives counts as "moved away" is not specified.
T-FR-10-4 defaults to treating any caret move as invalidating the pending request regardless of where the caret ends up, since that is the simplest reading of AC-10.3's "the caret moves away from the region."
If the intended behavior is that a same-position return should still show the result, T-FR-10-4 would need a second case for that return path.
