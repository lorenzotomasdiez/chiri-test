# FR-12: AI failure and offline behavior - Test Plan

| Field | Value |
|---|---|
| Requirement | [FR-12](../../prd/chiri/index.md#fr-12-ai-failure-and-offline-behavior) |
| Priority | P0 |
| Scenarios | 18 |
| Last updated | 2026-07-28 |

## What this requirement promises

When the model is unreachable or the provider errors, the document itself is never damaged, blocked, or held hostage.
The two failure classes are treated on opposite sides of the same line the rest of the product draws: continuation is unrequested, so its failures are invisible and editing simply continues; revision and refinement are requested, so their failures are always shown, dismissible, and retryable.
A rejected key is the one failure that overrides silence in either direction, because it is not really a request failure, it is the end of the session's authentication, and it always routes back through the FR-1 key gate with the document intact.

## Preconditions

A valid OpenRouter key has already been entered and confirmed per FR-1, so the app is unblocked and the editor is reachable.
A document with existing content is open, so revision and refinement scenarios have a span to select.
Continuation prediction is on, its default state per FR-10.
Provider responses in every scenario below are produced by intercepting the OpenRouter endpoint rather than by depending on real provider behavior, per the technical blueprint's testing seam of routing the network call.

## Scenarios

### T-FR-12-1: A continuation request fails silently when the network is unavailable
**Priority:** P0
**Covers:** AC-12.1

**Given** the network is unavailable and the user is typing a paragraph ending "the deployment pipeline now runs on every"
**When** the user pauses long enough that a continuation would normally be requested, and then keeps typing for 60 seconds total
**Then** no error message, banner, or indicator appears anywhere in the interface
**And** no grey continuation text appears at any point
**And** every character the user typed is present in the document exactly as typed

**How you would run this:** Fully automatable. The scheduler takes an injected transport per the blueprint's testing seam; a transport that rejects with a network error, combined with fake timers for the settle debounce, exercises this without a real network.

---

### T-FR-12-2: A revision request failure is visible, dismissible, and offers a retry
**Priority:** P0
**Covers:** AC-12.2

**Given** the network is unavailable and the user selects the paragraph "The onboarding flow needs a rewrite before launch." and clicks "Make it shorter"
**When** the request fails
**Then** a failure message appears at the selection within 10 seconds naming that the request did not complete
**And** the message carries a control to dismiss it and a control to retry
**And** the document still reads exactly "The onboarding flow needs a rewrite before launch." with no tracked-change diff shown

**How you would run this:** Fully automatable with `page.route` intercepting the OpenRouter endpoint and aborting or timing out the connection, per the testing seam's Playwright provider-error-response interception.

### T-FR-12-10: A malformed, empty, or truncated continuation response is treated as a silent failure
**Priority:** P0
**Covers:** AC-12.6

| Case | Provider response |
|---|---|
| Empty body | 200 response with zero content-bearing chunks |
| Malformed body | A response missing the expected sentinel structure |

### T-FR-12-11: A malformed, empty, or truncated revision response is treated as a visible, retryable failure
**Priority:** P0
**Covers:** AC-12.6

**When** the provider responds as described in the table below

| Case | Provider response |
|---|---|
| Empty body | 200 response with zero content-bearing chunks |
| Malformed body | A response missing the reason/sentinel structure the revision stream contract expects |

**How you would run this:** Fully automatable with a scripted transport per the provider-parsing module's testing seam; the stream-cut case is the one the blueprint explicitly flags as needing a "treat as failed per AC-12.6" rule rather than a best-effort render of whatever arrived.

**Priority:** P1

## What will probably break

The rate-limit auto-resume (AC-12.3) is the prediction most likely to be wrong first, because the blueprint states plainly there is no retry-with-backoff and recovery depends on the token bucket refilling rather than reading a `Retry-After` header; a sustained 429 will look identical to continuation simply having stopped working, and T-FR-12-5 needs a long enough rate-limited window to actually distinguish "paused" from "silently broken".

Malformed and truncated responses (T-FR-12-10, T-FR-12-11) are likely to be under-handled on the first pass, because the blueprint's own "What Will Bite" table names exactly this: a missing sentinel line causing the reason parser to swallow real content, and no explicit rule yet for what a mid-stream disconnect looks like versus a clean empty response; the stream-cut case in both scenarios is the one most likely to leave stale partial text on screen instead of a clean failure.

The precedence between an already-visible revision failure and a subsequent key rejection (T-FR-12-17) is unspecified in the requirement and is the kind of interaction two independent UI state machines get wrong in opposite directions on the first build, either stacking both messages or losing the key gate behind the older one.

Cross-browser cancellation-versus-failure behavior (T-FR-12-18) is flagged by the blueprint as unproven for real Safari.app, where a cancelled continuation stream may keep delivering data after abort; if that happens, a request the scheduler believes is dead could still resolve and risk being misrouted into either the silent continuation path or, worse, painted as if it succeeded.

## Not covered here

FR-1's key gate mechanics, states, and messaging (invalid key, incomplete check, account-restricted) are FR-1's own plan; this file only covers the trigger that a rejected key mid-session routes to that gate and that the document survives the round trip.

FR-7's refinement lifecycle beyond failure handling (multi-turn accumulation, dismiss-without-cancelling) is FR-7's own plan; T-FR-12-4 covers only the failure-and-revert behavior FR-12 owns.

FR-10's request scheduling internals (settle debounce values, concurrency ceiling, per-minute cap) are FR-10's own plan; T-FR-12-18 only checks that a cancellation resulting from that discipline is not mistaken for a failure.

NFR-1 suggestion latency and NFR-2 general input responsiveness are judged globally, not per requirement; T-FR-12-15 tests only the specific case of input responsiveness while a failure message is displayed, not the general bar.

Retry backoff strategy and exact request-per-minute recovery timing are explicitly deferred to the future architecture document per the requirement's own text, so no scenario here asserts a specific recovery interval, only that recovery eventually happens without user action.

## Open questions

Whether insufficient credit on a continuation request is silent (following the general class rule) or visible (if AC-12.5's wording is read as applying regardless of request class) is not settled by the requirement text.
T-FR-12-9 defaults to silent-for-continuation; if the intended reading is that credit exhaustion is always surfaced regardless of class, that scenario's expected result inverts and AC-12.5 itself would need a matching revision scenario added.

Whether a key rejection received while an unrelated revision failure message is already on screen replaces that message immediately or waits for the user to dismiss it first is not stated.
T-FR-12-17 defaults to immediate replacement; if the intended behavior is to let the user dismiss the older message first, that scenario's expected result changes.

Whether the revision failure message's retry action re-sends the exact same request (same span, same instruction) or requires the user to re-select and re-ask is not stated.
T-FR-12-12 assumes retry re-sends the same request without requiring re-selection; if retry instead requires the user to reselect, the scenario's Given/When changes.
