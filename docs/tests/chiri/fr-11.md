# FR-11: Empty-document onboarding cue - Test Plan

| Field | Value |
|---|---|
| Requirement | [FR-11](../../prd/chiri/index.md#fr-11-empty-document-onboarding-cue) |
| Priority | P1 |
| Scenarios | 10 |
| Last updated | 2026-07-28 |

## What this requirement promises
On a first-ever visit, Chiri shows an empty document plus one quiet, non-interactive cue that tells the user to start writing and how to accept a suggested continuation, instead of a tour, a modal, or seeded sample text.
The cue vanishes the instant the user produces the first character of content, and it never shows again while the document holds content.
If the user later empties a document back to nothing, the cue is allowed to come back, and typing dismisses it again without losing anything.

## Preconditions
FR-3 (live-preview Markdown editor) is in place: the editor renders and accepts keystrokes.
FR-4 (local persistence) governs whether a document survives a reload; these scenarios treat FR-4's save and load behavior as given and only check what the cue does around it.
A "first-ever session" means the browser profile has no previously saved Chiri document or settings, per AC-4.5.

## Scenarios

### T-FR-11-1: First-ever launch shows an empty document and a cue naming both actions
**Priority:** P0
**Covers:** AC-11.1, AC-11.2

**Given** a browser profile that has never opened Chiri before, with no document or settings in local storage
**When** the app loads and the editor is presented
**Then** the document contains zero characters
**And** the cue text names the action to start typing
**And** the cue text names the exact interaction to accept a suggested continuation
**And** no tour, walkthrough step, or modal dialog appears anywhere on screen
**And** no other cue, tooltip, or hint is shown at the same time

**How you would run this:** Needs a real browser (Playwright) per the blueprint's testing seams, since this asserts on the rendered `EditorView` and DOM, not the pure core; storage is faked via the injected `DocumentStore`/`Settings` interfaces starting empty.

### T-FR-11-2: Exported Markdown from a first-ever session contains no sample or placeholder text
**Priority:** P0
**Covers:** AC-11.1

**Given** the same first-ever, never-touched browser profile as T-FR-11-1
**When** the user exports the document immediately, without typing anything, using FR-9's export
**Then** the exported Markdown is an empty string
**And** it contains none of the cue's own wording

**How you would run this:** Needs a real browser to render the editor and trigger export; the export content check itself is a plain string assertion.

### T-FR-11-3: The cue is not interactive and never blocks input
**Priority:** P0
**Covers:** AC-11.2, `Beyond the stated criteria`

**Given** the cue is visible in an empty document
**When** the user clicks directly on the cue's text, and separately presses Tab and Enter while focus is on the page but before typing anything
**Then** nothing about the cue changes state, no dismiss control fires, and no focus trap occurs
**And** the editor is immediately focusable and the caret can be placed and typed into without any extra click or dismissal step

**How you would run this:** Needs a real browser under Playwright to exercise click and keyboard events against the live DOM; nothing here is fakeable in the pure core.

### T-FR-11-4: The first character of content dismisses the cue and is preserved
**Priority:** P0
**Covers:** AC-11.3

**Given** the cue is visible in an empty document
**When** the user produces their first content using the input method in the table
**Then** the cue is no longer present anywhere in the rendered page
**And** the document contains exactly the input given, with nothing else added or missing

| Case | First input | Expected document content after |
|---|---|---|
| Single letter | `H` | `H` |
| Single digit | `1` | `1` |
| Single space | ` ` (one space, typed) | ` ` |
| Multi-character paste | pasting `Hello there` in one action | `Hello there` |
| Newline | pressing Enter | a single newline character |

**How you would run this:** Needs a real browser under Playwright, since keydown, paste, and composition events all route through CodeMirror's `EditorView`; the pure core is not involved.

### T-FR-11-5: Deleting all content from a non-empty document brings the cue back, and typing dismisses it again with no loss
**Priority:** P1
**Covers:** AC-11.4

**Given** a document that already contains `Draft notes for the launch event` from earlier in the session
**When** the user removes every character, using the method in the table, leaving zero characters
**Then** the cue reappears
**When** the user then types `N`
**Then** the cue disappears again
**And** the document contains exactly `N`
**And** no fragment of `Draft notes for the launch event` is present anywhere in the document or in undo-adjacent state that the user did not explicitly request

| Case | Deletion method |
|---|---|
| Backspace to zero | Repeated Backspace until the document is empty |
| Select-all then delete | Ctrl/Cmd+A followed by Delete |
| Undo back to empty | Undo repeated until the document returns to its empty starting state |

**How you would run this:** Needs a real browser under Playwright for the editor interaction; the "no content loss" check reads the document state back through the same `DocumentStore` interface the blueprint marks as fakeable, so persistence itself can be faked while the editor stays real.

### T-FR-11-6: The cue never shows while the document has any content
**Priority:** P0
**Covers:** AC-11.2 (negative case), `Beyond the stated criteria`

**Given** a document containing `Meeting notes for Tuesday`
**When** the user clicks elsewhere on the page and refocuses the editor, and separately when the user scrolls the document or resizes the window
**Then** the cue is not shown at any point during these actions
**And** the cue is absent regardless of caret position, selection state, or scroll position

**How you would run this:** Needs a real browser under Playwright to check the rendered DOM across these interactions.

### T-FR-11-7: Reloading a document with content never shows the cue
**Priority:** P0
**Covers:** AC-11.4, `Beyond the stated criteria`

**Given** a document containing `Meeting notes for Tuesday` was saved in a prior session, per FR-4
**When** the user reloads the page
**Then** the restored document shows `Meeting notes for Tuesday`
**And** the cue is not shown

**How you would run this:** Needs a real browser under Playwright with the injected `DocumentStore` preloaded with saved content, per the blueprint's persistence seam.

### T-FR-11-8: A returning user whose document is still empty sees the cue again
**Priority:** P1
**Covers:** `Beyond the stated criteria`

**Given** a user opened Chiri previously, typed nothing, and closed the browser, so the saved document is present but has zero characters
**When** the user reopens Chiri in the same browser profile
**Then** the document is empty
**And** the cue is shown exactly as it was on the very first visit

**How you would run this:** Needs a real browser under Playwright with the injected `DocumentStore` preloaded to an empty-but-saved state, distinguishing "no document ever saved" from "a document was saved and it happens to be empty."

### T-FR-11-9: The cue's instructional text is exposed to assistive technology, not only sighted users
**Priority:** P1
**Covers:** `Beyond the stated criteria` (NFR-6 touches this requirement because the cue is the only place the accept-continuation interaction is documented for a first-time user)

**Given** the cue is visible in an empty document
**When** a screen reader user navigates to the editor region using keyboard-only navigation
**Then** the cue's text, including the accept-continuation instruction, is announced or otherwise exposed through the accessibility tree
**And** the cue's presence does not rely on color alone to be noticed

**How you would run this:** Manual check with a real screen reader (VoiceOver and NVDA per the blueprint's open question on the accept-key binding); automatable in part with an accessibility-tree query under Playwright for the accessible name/description, but full announcement behavior needs a live reader.

### T-FR-11-10: The cue's stated accept-continuation instruction matches the actual accept keystroke
**Priority:** P0
**Covers:** AC-11.2, `Beyond the stated criteria`

**Given** the cue is visible in an empty document, and continuation prediction is on by default per FR-10
**When** the user reads the cue's wording for how to accept a continuation, then later triggers and accepts a continuation using that exact keystroke
**Then** the keystroke named in the cue is the same keystroke that actually accepts a continuation in the editor
**And** no separate, undocumented keystroke is required

**How you would run this:** Needs a real browser under Playwright to drive the editor, a faked transport for the continuation response (per the blueprint's ghost-text testing seam), and a string comparison between the cue's rendered text and the bound key.

## Boundaries checked

| Value or limit | Just below | At | Just above | Scenario |
|---|---|---|---|---|
| Characters in document, cue-hides-on-first-content transition | Not applicable, document length cannot go below 0 | 0 characters, cue shown | 1 character, cue hidden | T-FR-11-4 |
| Characters in document, cue-reappears-on-emptying transition | 1 character remaining, cue absent | 0 characters after full deletion, cue shown | Not applicable, deletion cannot continue past 0 | T-FR-11-5 |

## What will probably break
The cue's accept-continuation wording is written against a keybinding that the blueprint's own open question 7 has not settled: Tab is the natural default but risks trapping keyboard and screen-reader focus, and the fallback under discussion is a different binding such as Ctrl+Enter.
T-FR-11-10 exists specifically to catch the day the binding changes and nobody updates the cue's copy to match, leaving the app telling users to press a key that does nothing.

The simplest implementation path is a CodeMirror placeholder-style overlay, but a careless implementation could instead insert the cue's own text as real document content and then hide it with styling, which would make it survive into the exported Markdown or get treated as the user's "first character."
T-FR-11-1 and T-FR-11-2 both check the exported Markdown specifically because that is where this mistake becomes visible; a purely visual check of the editor would miss it.

Emptiness detection is likely to be implemented as `document.text.length === 0`, which will not agree with a human's sense of "empty" once whitespace, a single space, or a lone newline is involved.
T-FR-11-4's space and newline rows, and the open question below, exist because the requirement does not say whether whitespace-only content counts as empty for the cue's reappearance logic, and the first implementation is likely to pick one silently.

Dismissal is likely wired to a `keydown` handler on the editor, which will miss paste events and IME composition (accented characters, CJK input) that never fire a matching `keydown` for the inserted character.
T-FR-11-4's paste row exists to catch a cue that lingers on screen after pasted content has already appeared underneath it.

## Not covered here
The mechanics of what makes a continuation appear and how it streams in belong to FR-5 and FR-10; this plan only checks that the cue's stated accept keystroke matches reality (T-FR-11-10), not the continuation feature itself.
Persistence correctness (debounce timing, survival of a hard browser kill, restore-on-reload fidelity) belongs to FR-4; here it is only a precondition for distinguishing "never saved" from "saved and empty" (T-FR-11-8).
The cue's exact wording, visual placement, and styling are explicitly left to the future design document by the requirement itself, so no scenario here pins specific copy or pixel position beyond the two things the requirement mandates the cue must convey.
General WCAG 2.1 AA contrast checks across the whole app are a global non-functional bar and are not re-tested per requirement here beyond T-FR-11-9's narrow check that the cue's own content is perceivable to assistive technology.

## Open questions
Whether a document containing only whitespace (a single space, a run of spaces, or a bare newline with no other content) counts as "empty" for the purpose of showing or re-showing the cue is not stated by the requirement.
Default interpretation used above: any character at all, including whitespace, counts as content and dismisses the cue, and the cue does not reappear until the document is truly zero-length.
If the intended interpretation is that whitespace-only content should still count as empty, T-FR-11-4's space and newline rows and T-FR-11-5's deletion boundary would need to change to test whitespace as a non-dismissing case instead.

Whether the cue is scoped per browser profile forever, or resets under some condition other than "document becomes non-empty then empty again" (for example, a settings reset or a manually cleared document via some future feature), is not stated.
Default interpretation used above: the cue's visibility is a pure function of current document emptiness, with no separate "have I ever shown this before" flag, consistent with AC-11.4 allowing reappearance.
If a one-time-only interpretation is intended instead, T-FR-11-8 would need to change to expect no cue on the second empty visit.
